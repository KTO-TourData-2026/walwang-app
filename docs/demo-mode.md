# 데모 / 실사용 모드 규약

왈왕은 **실사용 버전**과 **데모 버전** 두 모드를 하나의 앱에서 오간다. 이 문서는 두 모드의
정의·전환 방식·데이터 규약·UX 규칙·구현 가이드를 한 곳에 모은 단일 소스다. 데모 관련 작업은
반드시 이 문서를 따른다.

> 관련: [prd.md](prd.md) · [user-flow.md](user-flow.md) · [api-architecture.md](api-architecture.md) · 이슈 [#36](https://github.com/KTO-TourData-2026/walwang-app/issues/36)

## 1. 왜 두 모드인가 (배경)

왈왕은 **리뷰 기반 신뢰도** 서비스라 시연 시점엔 실제 리뷰가 없어 목(mock) 리뷰가 필요하다.
그런데 관광공사 OpenAPI로 가져온 **실제 상호명 + 가짜 리뷰(반려동물 가능/불가)** 를 그대로
배포하면 문제가 생긴다.

- **법적 리스크** — 실제 상호에 "불가능" 같은 가짜 리뷰를 붙이면 구글 플레이 **기만행위 정책 위반**
  및 **명예훼손**(형사처벌 소지)에 걸릴 수 있다.
- **심사 딜레마** — 그렇다고 전부 마스킹만 하면, 1차 심사의 **핵심 포인트인 "관광공사 API를
  실제로 쓰는지"** 를 심사위원이 확인하기 어렵다.
- **OCR 모순** — 영수증 OCR은 상호명을 마스킹해도 실제 상호명과 일치해야 동작한다.

→ 이 셋을 동시에 만족시키기 위해 **모드를 분리**한다.

|                 | **실사용 버전**                                 | **데모 버전**                                          |
| --------------- | ----------------------------------------------- | ------------------------------------------------------ |
| 목적            | 바로 사용 가능한 실서비스 + **API 실사용 증명** | "데이터가 쌓이면 이렇다"를 보여주는 시연               |
| `demo` 파라미터 | `false` (기본값)                                | `true`                                                 |
| 리뷰            | 가짜 없음. 실사용자가 OCR 인증으로만 등록       | 목 리뷰 노출                                           |
| 상호명          | 실제 상호명 그대로                              | **백엔드가 가상 상호명으로 마스킹**("카페 1"·"식당 1") |
| 영수증 OCR      | 실제 동작                                       | **생략**(실상호 매칭 문제 회피)                        |
| 반려견 사진     | 인앱 카메라/갤러리                              | 인앱 카메라/갤러리 (동일, 실제 업로드)                 |
| 모드 표시       | real/demo 토글 상시 노출                        | real/demo 토글 상시 노출 + 데모 진입 시 안내 모달      |

## 2. 전환 방식

- **런타임 인앱 토글.** 로그인·회원가입 이후 **전 화면(인증 전 제외)에 하단 중앙 플로팅**으로 작은
  real/demo 토글을 **양쪽 모드 모두 상시** 노출하고, 사용자가 자유롭게 실사용 ↔ 데모를 오갈 수
  있다. 이 토글이 곧 현재 모드 표시이자 안내 모달(§6-1) 진입점이다.
- **기본값은 실사용(`demo=false`).** 앱스토어에 올라가는 것도 실사용 기본 상태다.
- 모드는 **런타임 상태**이며 앱을 재실행해도 유지되도록 **로컬에 영속**한다.
- 빌드 상수(`DEMO_MODE`)로 두지 않는다 — 하나의 빌드에서 토글로만 바뀐다.

> ⚠️ **모드를 바꾸면 보이는 데이터 공간이 통째로 바뀐다**(§4). 전환 시 **React Query 캐시를
> 비워** 실사용/데모 데이터가 섞이지 않게 한다. 자세한 건 §7 구현 가이드.

## 3. `demo` 파라미터 규약 (백엔드 스펙)

- **HTTP 쿼리 파라미터**다(요청 body 아님). 예: `GET /stores?...&demo=true`.
- **미지정 시 기본 `false`.** 실사용에서는 붙이지 않아도 되지만, 프론트는 **경계에서 항상 현재
  모드 값을 명시적으로 넘긴다**(§7).
- 마스킹·목 리뷰 노출·집계 격리는 **전부 백엔드가 `demo` 값으로 처리**한다. 프론트는 받은 값을
  그대로 렌더할 뿐 이름을 가공하지 않는다.

### 붙는 엔드포인트

| 구분 | 엔드포인트                      | 비고                                                                   |
| ---- | ------------------------------- | ---------------------------------------------------------------------- |
| 조회 | `GET /stores`                   | 지도 목록                                                              |
| 조회 | `GET /stores/search`            | 검색 — 데모는 검색결과 **전체 마스킹**(백엔드 구현 완료)               |
| 조회 | `GET /stores/{id}`              | 가게 상세 — `possibleCount`/`impossibleCount`·`sizeStatus[]` demo 집계 |
| 조회 | `GET /stores/{id}/reviews`      | 가게 리뷰 — 데모 본인 리뷰는 본인만 노출                               |
| 조회 | `GET /stores/{id}/alternatives` | 거절 완료 대체 장소                                                    |
| 조회 | `GET /user/store`               | 저장 장소 목록                                                         |
| 조회 | `GET /user/me/saved-courses`    | 저장 코스 목록                                                         |
| 조회 | `GET /user/me`                  | 프로필 — `reviewCount`·`stampCount`                                    |
| 조회 | `GET /user/me/reviews`          | 내 리뷰 목록                                                           |
| 조회 | `GET /user/me/passport`         | 여권(도장) 목록                                                        |
| 조회 | `GET /user/me/passport/{id}`    | 여권 상세 — 공간 불일치 시 404 (§4)                                    |
| 조회 | `GET /courses/{id}`             | 코스 상세 — 공간 불일치 시 404 (§4)                                    |
| 조회 | `POST /courses/recommend`       | 코스 추천(조회 성격)                                                   |
| 쓰기 | `POST /reviews`                 | **`true`면 영수증 인증 없이 등록**                                     |
| 쓰기 | `POST /reviews/receipt-verify`  | OCR용 — **데모에선 아예 호출하지 않는다**                              |
| 쓰기 | `POST /stores/{id}/save`        | 장소 저장                                                              |
| 쓰기 | `DELETE /stores/{id}/save`      | 장소 해제 — 저장과 대칭으로 demo 추가됨                                |
| 쓰기 | `POST /courses`                 | 코스 저장                                                              |

### 예외 (demo 미부착)

- **코스 이름변경·삭제**(`PATCH`/`DELETE /courses/{id}`)는 `demo`를 붙이지 않는다.
  courseId 자체로 대상이 특정되므로 공간 구분이 불필요하다.

## 4. 데이터 공간 격리 규칙 (중요)

`demo=true`와 `demo=false`는 **완전히 분리된 데이터 공간**이다. 섞으면 404 또는 빈 집계가 난다.
프론트는 이 전제 위에서 동작해야 한다.

- **코스 상세·여권 상세** (`GET /courses/{id}`, `GET /user/me/passport/{id}`)
  → 데모에서 만든 걸 실사용에서 열면 **404**(반대도 마찬가지).
- **저장 장소·저장 코스** (`GET /user/store`, `GET /user/me/saved-courses`)
  → 데모에서 저장한 건 **데모에서만** 보인다.
- **프로필** (`GET /user/me`) → 데모 중 개인 리뷰 수·도장 수는 정상 반영되지만, **가게 집계에는
  사용자가 만든 목 리뷰가 반영되지 않는다**.
- **가게 리뷰** (`GET /stores/{id}/reviews`) → 데모에서 **본인이 쓴 리뷰는 본인에게만** 보인다.

→ 그래서 **모드 전환 시 캐시를 비우는 것**(§2)이 규약이다. 캐시가 남으면 실사용 화면에 데모
데이터가 잔상으로 보일 수 있다.

## 5. 마스킹 · 목 리뷰 규약 (안전 시연 3대 조건)

주최측 자문 기준. 데모 데이터를 만들거나 노출할 때 반드시 지킨다.

1. **유추 불가능한 가짜 상호명** — 실제 브랜드가 연상되면 안 된다.
   - ❌ `스타벅스 강남점 → 스벅 강남` (브랜드 연상·상표권 소지)
   - ✅ `스타벅스 강남점 → 카페 1` / `초록달 카페` (실명 일부도 남기지 않는다)
   - 마스킹은 백엔드가 수행한다. 프론트는 받은 이름을 **가공 없이 그대로** 표시한다.
2. **누가 봐도 가짜인 리뷰** — 실제 매장 평판으로 오해될 여지를 없앤다.
   - **부정·거절 리뷰 제외**, 조건 안내·중립 묘사만. `"파스타 맛있어요"` 같은 그럴싸한 내용 금지.
   - 리뷰에 `[시연용 목데이터입니다]` 같은 명시 문구를 넣는다.
   - **앱스토어 배포 시 거절 리뷰 목데이터는 제거**한다(§9).
3. **앱 내 데모 안내 문구** — §6 토글·안내 모달로 노출한다.

## 6. 데모 UX 규약

### 6-1. 모드 토글 · 안내 모달

큰 고정 배너 대신 **작은 real/demo 토글**을 **전 화면(로그인·회원가입·스플래시 제외)에 하단
중앙 플로팅**으로 상시 노출한다. 세그먼트 탭 → **즉시 전환**(확인 다이얼로그 없음), 옆 ⓘ 탭 →
안내 모달. **데모 모드일 때는 토글 옆에 `모든 데이터는 목 데이터입니다` 상시 문구**를 함께
노출한다(§5-3 "명시").

**자동 노출** — 주최측 자문(§5-3)의 "명시" 기준을 만족시키기 위해, **로그인·회원가입 최초 진입
(토큰 발급) 시 안내 모달을 1회 자동 노출**한다. 모달에 **"오늘 하루 다시 보지 않기"** 를 두어,
같은 날 재로그인 시엔 자동 노출을 건너뛴다. 이 하루 억제는 **로컬에 날짜(`YYYY-MM-DD`)만
저장하는 클라이언트 처리라 API가 필요 없다**(§7-2). 자동 노출과 별개로, 토글 탭으로는 언제든
다시 열람할 수 있다.

안내 모달은 모드별 문구가 아니라 **실사용·데모 차이를 함께 설명하는 전체 안내문**이며, 아래
데모 disclosure 원문을 그 안에 포함한다:

> **본 앱은 시연용 데모 버전입니다.** 위치 및 장소 API 기능 시연을 위해 실제 매장 정보를 가상의
> 상호명으로 치환하여 표시하고 있으며, 노출되는 리뷰는 모두 가상의 목(Mock) 데이터입니다.

### 6-2. 데모 리뷰 작성 플로우

데모에서는 영수증 OCR을 실제로 돌릴 수 없다(실상호명 매칭 불가). 대신 **튜토리얼형**으로 흐름만
체험시킨다. 리뷰 진입·결과 선택(들어갔어요/거절)은 실사용과 동일하다.

**"들어갔어요" 경로 (영수증 단계)** — `review/[placeId]/receipt`:

1. 카메라 화면 대신 **"현재 데모 모드라 영수증 인증은 실제로 체험할 수 없어요"** 튜토리얼 안내를
   띄운다. 실사용에서 나올 수 있는 여러 결과(인증 성공/판독 실패/상호 불일치)를 **설명용으로**
   보여줄 수 있다.
2. 실제 검증(`receipt-verify`) 호출 없이 **"상호명 인식 완료" 상태로 임의 통과**시킨다.
3. 이후 **반려견 사진 업로드는 사용자가 실제로** 진행한다(인앱 카메라/갤러리 그대로).
4. 내용·태그 작성 후 등록은 `POST /reviews?demo=true`로 **영수증 토큰 없이** 등록된다.

**"거절당했어요" 경로** — 실사용과 동일(영수증 없음, 바로 폼).

### 6-3. 목 리뷰 집계 미반영 고지

데모에서 사용자가 목 리뷰를 등록해도 **판정·집계 로직상 리뷰 수/가게 집계에는 반영되지
않는다**(§4). 등록 완료(done) 화면 등에 짧게 고지한다:

> 데모에서 등록한 리뷰는 **본인에게만** 보이며, 가게의 리뷰 수 집계에는 반영되지 않아요.

## 7. 구현 가이드

**구현 완료(런타임화, 이슈 [#38]).** `src/api/demo.ts`는 빌드 상수 대신 모듈 지역 변수 + 접근자
(`getDemoMode`/`setDemoModeFlag`)로 바뀌었고, store·review·course·user API가 `params.demo`로
`getDemoMode()`를 넘긴다. 모드는 `src/stores/demo-mode.ts`(zustand + `expo-secure-store` 영속)가
관리한다. (데모 리뷰 작성 튜토리얼 분기(§6-2·§7-3)는 후속 이슈 B에서 다룬다 — 아직 미구현.)

### 7-1. 모드 상태 (런타임화)

API 함수는 훅이 아니라 axios 호출부라 **동기적으로 현재 값을 읽어야** 한다. 영속 상태는 zustand로
두되, API 경계는 모듈 변수로 읽는다.

- `src/stores/demo-mode.ts` (신규) — zustand + 영속(`expo-secure-store`, 토큰과 같은 저장소 재사용).
  `{ isDemo, setDemo, ... }`. `setDemo`에서 아래 두 가지를 함께 수행한다:
  1. `src/api/demo.ts`의 모듈 값 동기화,
  2. `queryClient.resetQueries()`로 캐시를 비우고 마운트된 화면까지 재조회(§4).
     `clear()`는 캐시 엔트리만 지우고 이미 떠 있는 화면(active observer)을 refetch하지 않아
     옛 데이터가 남으므로 `resetQueries`를 쓴다.
- `src/api/demo.ts` — 상수 대신 **모듈 지역 변수 + 접근자**로 교체:
  ```ts
  let demoMode = false;
  export const getDemoMode = () => demoMode;
  export const setDemoModeFlag = (v: boolean) => {
    demoMode = v;
  };
  ```
- 각 API 파일의 `params: { demo: DEMO_MODE }` → `params: { demo: getDemoMode() }`로 교체.
  (store·review·course·user 전부. 예외 §3 그대로 유지.)

### 7-2. 토글 UI + 안내 모달

- `src/components/demo/`에 real/demo 토글(`demo-mode-toggle.tsx`)·전체 안내 모달
  (`demo-mode-notice-modal.tsx`)과, 이를 전 화면 공통으로 띄우는 플로팅 오버레이
  (`demo-mode-floating-toggle.tsx`)를 둔다. 오버레이는 **루트 레이아웃**(`src/app/_layout.tsx`)에서
  Stack 형제로 한 번만 렌더한다. **하단 중앙**에 두되 화면 유형별로 탭바/버튼바 위로 띄우고,
  로그인·회원가입·스플래시와 전체화면 모달에선 숨긴다. 세그먼트 탭 → `useDemoMode().setDemo(...)`
  (즉시 전환).
- 옆 ⓘ 탭 → 전체 안내 모달(문구 §6-1). 데모일 때는 토글 옆에 상시 disclosure 문구.
- **로그인·회원가입 성공 시 `maybeAutoShowNotice()`로 안내 모달 1회 자동 노출**(§6-1). "오늘 하루
  다시 보지 않기"는 로컬에 날짜(`YYYY-MM-DD`)만 저장해 비교 — **API 불필요**. 저장은 모드
  스토어와 같은 `expo-secure-store`. (체크하지 않으면 새 로그인마다 노출되는 게 기본이며, 토큰이
  유지되는 앱 재실행에선 뜨지 않는다.)

## 8. 백엔드 후속 확인

집계성 응답이 `demo=true` 데이터를 반영하지 않던 이슈들(PR
[#35](https://github.com/KTO-TourData-2026/walwang-app/pull/35)) 처리 현황.

**해결됨**

- ✅ **가게 상세 카운트** — `/stores/{id}?demo=true`의 `possibleCount`/`impossibleCount` 및
  `sizeStatus[]`가 이제 demo에 따라 집계된다. (앱은 이 둘의 합을 "전체 리뷰 수"로 표시)
- ✅ **`DELETE /stores/{id}/save`에 `demo` 파라미터 추가** — 저장(POST)과 대칭으로 해제(DELETE)에도
  demo가 붙어 스펙이 정합됐다.
- ✅ **여권 도장 집계** — `GET /user/me/passport?demo=true` 및 `/user/me`의 `stampCount`가 이제
  demo 공간 기준으로 집계된다.
